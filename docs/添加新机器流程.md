# 添加新多方块机器的流程

以「真空冷冻机」（`GTVacuumCooler*`）和「进阶化学反应釜」（`GTAdvancedChemicalReactor*`）为样板，记录从头加一台多方块机器的完整清单。

**核心设计**：方块类 `GTChemicalReactorMachineBlock` 和实体类 `GTChemicalReactorMachineBlockEntity` 是共享的，新机器只注册、不复制。所有差异通过覆写钩子表达。

---

## 一、必须理解的四条铁律

### 1. 结构文件要放两份

| 位置 | 谁读 | 用途 |
|---|---|---|
| `data/goldentweaks/multiblock/structures/<id>.json` | 服务端 | 结构校验、一键建造 |
| `assets/goldentweaks/multiblock/structures/<id>.json` | 客户端 | 投影仪预览 |

**两份内容必须完全一致。** 客户端用的是 `SimpleJsonResourceReloadListener`，它只读 `assets/`。只放 `data/` 的话，服务端能成型、投影仪却什么都画不出来。

### 2. 方块 id 决定一切，不要在代码里硬编码机器 id

过去散落着 `GTChemicalReactorMultiblock.MACHINE.get()`、`HOST_STRUCTURES` 映射表这类硬编码，导致进阶机器：界面秒关、投影仪失效、拆除还错方块。现在全部收敛到两个地方：

- **方块**携带自己的结构 id、实体工厂、机壳（构造参数 `structurePath` + `tileFactory` + `casing`）
- **实体**通过 `getMachineId()` / `menuType()` 等虚方法作答

新机器只需注册时传参，不再需要改任何共享代码。

### 3. 客户端屏幕必须注册，否则界面「打开即关闭」

服务端 `openMenu` 永远成功。客户端拿到一个**没有注册 Screen 的 MenuType** 时，会在同一 tick 把窗口关掉——表现就是「右键没反应」。

`GTChemicalReactorClientEvents.registerScreens` 里每台机器都要一行。这是最容易漏的一步，因为它不报任何错。

### 4. 端口机壳索引 = `CASINGS` 里的下标，blockstate 必须覆盖全部

`GTMultiblockBlocks.CASINGS` 目前是 `[SHELL_PE, SHELL_PP, SHELL_ALUMINUM]`，下标 0/1/2。

装配时机器会把自己的机壳索引写进每个仓室的 `CASING` 属性：

```java
int casingIndex = GTMultiblockBlocks.casingIndex(casingBlock());   // 铝 -> 2
level.setBlock(pos, portState.setValue(GTPortBlock.CASING, casingIndex), ...);
```

**205 个 `gt_port_*.json` 的 blockstate 必须都有 `casing=<每个下标>` 的变体**，否则该索引无匹配 → 缺模型 → **紫黑方块**。

> 这个坑踩得很隐蔽：反应釜用 PE/PP（0/1）时一切正常，直到第一台铝合金机器出现才暴露。

## 二、Java 侧（5~7 个文件）

### 2.1 注册类

新建 `compat/avaritia_more_items/GTXxxMultiblock.java`，照抄 `GTVacuumCoolerMultiblock`：

```java
public final class GTVacuumCoolerMultiblock {

    /** 方块注册 id */
    public static final String ID = "vacuum_cooler_controller";

    public static final DeferredRegister.Blocks BLOCKS = DeferredRegister.createBlocks(GoldenTweaks.MODID);
    public static final DeferredRegister.Items ITEMS = DeferredRegister.createItems(GoldenTweaks.MODID);
    public static final DeferredRegister<BlockEntityType<?>> BLOCK_ENTITIES =
            DeferredRegister.create(Registries.BLOCK_ENTITY_TYPE, GoldenTweaks.MODID);
    public static final DeferredRegister<MenuType<?>> MENU_TYPES =
            DeferredRegister.create(Registries.MENU, GoldenTweaks.MODID);

    /** 菜单类型：客户端靠它选界面类 */
    public static final DeferredHolder<MenuType<?>, MenuType<GTChemicalReactorMenu>> MENU =
            MENU_TYPES.register("vacuum_cooler", () -> IMenuTypeExtension.create(
                    (containerId, inventory, data) ->
                            GTChemicalReactorMenu.create(menuType(), containerId, inventory,
                                    data.readBlockPos())));

    private static MenuType<?> menuType() {   // 必须用方法，否则自引用编译不过
        return MENU.get();
    }

    /** 方块：复用同一个类。参数依次是 属性 / 结构文件名 / 实体工厂 / 机壳 */
    public static final DeferredBlock<GTChemicalReactorMachineBlock> MACHINE =
            BLOCKS.register(ID,
                    () -> new GTChemicalReactorMachineBlock(GTMultiblockBlocks.properties(),
                            GTVacuumCoolerBlockEntity.MACHINE_ID,
                            GTVacuumCoolerBlockEntity::new,
                            GTMultiblockBlocks.SHELL_ALUMINUM));

    /** 物品：第三个参数是 tooltip 里显示的机壳语言键 */
    public static final DeferredItem<BlockItem> MACHINE_ITEM =
            ITEMS.register(ID,
                    () -> new GTVacuumCoolerItem(MACHINE.get(), new Item.Properties(),
                            "block.goldentweaks.shell_aluminum"));

    /** 方块实体类型：必须与方块一一对应，否则放置时崩溃 */
    public static final DeferredHolder<BlockEntityType<?>,
            BlockEntityType<GTVacuumCoolerBlockEntity>> MACHINE_ENTITY =
            BLOCK_ENTITIES.register(ID,
                    () -> BlockEntityType.Builder.of(
                            GTVacuumCoolerBlockEntity::new, MACHINE.get()).build(null));

    public static void register(IEventBus eventBus) {
        BLOCKS.register(eventBus);
        ITEMS.register(eventBus);
        BLOCK_ENTITIES.register(eventBus);
        MENU_TYPES.register(eventBus);
        GTVacuumCoolingRecipes.register(eventBus);   // 若有独立配方类型
    }
}
```

**易错点**：

- `MACHINE_ENTITY` 的 id 必须与 `MACHINE` 的 id 一致。不一致会在放置时抛 `Invalid block entity`
- 忘了注册 `MENU_TYPES` → 界面打不开
- 忘了在 `GTChemicalReactorClientEvents` 注册屏幕 → 界面一打开就关闭

### 2.2 实体类

新建 `compat/avaritia_more_items/GTXxxBlockEntity.java`，继承 `GTChemicalReactorMachineBlockEntity`：

```java
public class GTVacuumCoolerBlockEntity extends GTChemicalReactorMachineBlockEntity {

    /** 结构文件名 */
    public static final String MACHINE_ID = "vacuum_cooler";

    public GTVacuumCoolerBlockEntity(BlockPos pos, BlockState state) {
        this(GTVacuumCoolerMultiblock.MACHINE_ENTITY.get(), pos, state);
    }

    public GTVacuumCoolerBlockEntity(BlockEntityType<?> type, BlockPos pos, BlockState state) {
        super(type, pos, state);
    }

    @Override public String getMachineId()       { return MACHINE_ID; }
    @Override protected Block casingBlock()      { return GTMultiblockBlocks.SHELL_ALUMINUM.get(); }
    @Override protected String nameKey()         { return "block.goldentweaks.vacuum_cooler_controller"; }
    @Override protected MenuType<?> menuType()   { return GTVacuumCoolerMultiblock.MENU.get(); }

    /** 配方集。只跑自己的，或前置基础版，按语义决定 */
    @Override protected List<RecipeType<GTChemicalReactionRecipe>> recipeTypes() {
        return List.of(GTVacuumCoolingRecipes.TYPE.get());
    }
}
```

**钩子清单**，漏一个就会出现诡异现象：

| 钩子 | 漏掉的后果 |
|---|---|
| `getMachineId()` | 读基础版的结构文件 |
| `casingBlock()` | 机壳数量校验用错材料 |
| `nameKey()` | 界面标题显示基础版名字 |
| `recipeTypes()` | 机器查不到自己的配方（默认只查基础釜那套） |
| `menuType()` | **界面一打开就关闭** |
| `machineParallelCeiling()` | 可选；返回 0 表示不额外限并行 |

> `getPatternId()` 不用覆写，它已经由 `getMachineId()` 拼出来。

**关于 `recipeTypes()` 的语义**（这里容易想当然）：

- 返回**多个**类型 = 机器同时接受这几套配方（进阶釜就是「自己的 + 基础釜的」）
- 返回**单个**类型 = 只跑这一套

如果新机器只是「换机壳的基础釜」，把基础版也列进去；如果它做的是**另一类工艺**（如真空冷冻），就只列自己那套，否则玩家会看到一台跑不了那些配方的机器仍被列为催化剂。

### 2.3 配方类型（若机器有独立配方集）

新建 `GTXxxRecipes.java`：

```java
public static final String DIRECTORY = "vacuum_cooling";

public static final DeferredHolder<RecipeType<?>, RecipeType<GTChemicalReactionRecipe>> TYPE =
        TYPES.register(DIRECTORY,
                () -> RecipeType.simple(ResourceLocation.fromNamespaceAndPath(GoldenTweaks.MODID, DIRECTORY)));

public static final DeferredHolder<RecipeSerializer<?>,
        GTChemicalReactionRecipe.Serializer> SERIALIZER =
        SERIALIZERS.register(DIRECTORY, () -> new GTChemicalReactionRecipe.Serializer(TYPE.get()));
```

序列化器可以复用基础版的（JSON 形状一样），但**类型必须独立**，否则两台机器会抢同一批配方。

**并且要在 `GTXxxMultiblock.register()` 里调用 `GTXxxRecipes.register(eventBus)`**——忘了注册类型，配方文件会被静默忽略。

### 2.4 客户端界面（可选，只有换贴图/换图标/换文案时才要）

```java
public class GTAdvancedChemicalReactorScreen extends GTChemicalReactorScreen {

    @Override
    protected ResourceLocation texture() { /* 自己的贴图 */ }

    /** 并行面板的图标。注意是「并行」不是「超频」 */
    @Override
    protected ItemStack parallelIcon() {
        return new ItemStack(GTMultiblockBlocks.CONTROL_CIRCUIT_PARALLEL_4X.get());
    }

    /** 并行面板标题下那一行 */
    @Override
    protected Component parallelCeilingLabel() { /* 自定义 */ }

```

**可覆写的界面钩子**：

| 方法 | 作用 |
|---|---|
| `texture()` | 窗体贴图 |
| `parallelIcon()` | 并行面板图标 |
| `parallelCeilingLabel()` | 并行面板标题下的说明 |
| `overclockIcon()` / `ratioLabel()` | **private，不可覆写**（超频面板全机一致） |

> 别搞混：要换的是**并行**面板。超频面板（4/2）在所有机器上是一样的。

然后在 `GTChemicalReactorClientEvents.registerScreens` 里加一行：

```java
event.register(GTVacuumCoolerMultiblock.MENU.get(), GTVacuumCoolerScreen::new);
```

共用界面类时直接传父类构造器引用即可；需要换贴图才写子类。

**换贴图的完整步骤**（三步，漏一步就有问题）：

1. 新建子类覆写 `texture()`
2. 贴图放到 `assets/goldentweaks/textures/gui/`（**不是** `textures/block/`，那里是方块贴图）
3. **在 EMI 插件里补一条 `addScreenBoundsProvider`**：

```java
registry.addScreenBoundsProvider(GTVacuumCoolerScreen.class,
        GTChemicalReactionEmiPlugin::kettleBounds);
```

> EMI **按精确类匹配** provider，父类那条不会被子类继承。漏了这条，EMI 的配方面板会直接盖在侧栏上。
>
> 这条坑很隐蔽：屏幕本身能用、贴图也正常，只有在打开配方查看器时才看得出错位。

> 换贴图前先确认新图与 `gt_multiblock_machine.png` 的布局一致（槽位、进度条、侧栏位置）。只换配色是安全的；布局不同的图直接套会控件错位——因为坐标全写在屏幕类里，不读图。

### 2.8 配方查看器（EMI / JEI）

若机器有独立配方类型，两侧都要注册类别，否则玩家看不到配方。

**EMI**（`GTChemicalReactionEmiPlugin` + `GTChemicalReactionEmiRecipe`）：

```java
// 类别常量
public static final EmiRecipeCategory VACUUM_CATEGORY = category("vacuum_cooling", <机器物品>);

// 注册
registry.addCategory(VACUUM_CATEGORY);
registry.addWorkstation(VACUUM_CATEGORY, EmiStack.of(<机器物品>));
registry.getRecipeManager().getAllRecipesFor(GTXxxRecipes.TYPE.get())
        .forEach(h -> registry.addRecipe(new GTChemicalReactionEmiRecipe(
                h.id(), h.value(), registries, VACUUM_CATEGORY)));
```

**JEI**（`GTChemicalReactionJeiPlugin` + `GTChemicalReactionJeiCategory`）三处都要加：`registerCategories` / `registerRecipes` / `registerRecipeCatalysts`。

> JEI 插件在 EMI 存在时会整体停用（`shouldLoad()`），所以纯 EMI 整合包只需 EMI 侧；但两个都写才能覆盖所有环境。
>
> **催化剂只加给能跑那套配方的机器**。机器只跑自己的配方集时，不要把它加成基础釜类别的工作站。

配方页面的标题用 `emi.category.goldentweaks.<DIRECTORY>` 这个语言键。

### 2.9 配方匹配链路（写自定义匹配规则时必读）

AMI 的 `MatchedMultiblockRecipe` 在被构造的那一刻就把 `recipe.getItemInputs()` 抽成一份 `ItemStack` 快照**冻结**，之后所有匹配都只比这份快照。这意味着**配方自己的 `matches()` 永远不会被调用**——除非你把链路截断。

`GTReactionMatcher`（自研匹配器）就是为了绕开这点：它支持「按 id 匹配、忽略组件」（`any_components`），AMI 的精确比较做不到。

**完整链路有四个节点，任何一处仍走 AMI 就会失败**：

| 位置 | 代码 | 状态 |
|---|---|---|
| 配方本身 | `GTChemicalReactionRecipe.matches()` | 已改为调 `GTReactionMatcher` |
| 搜索 | `matchRecipesOfMode` → `recipe.matches(input, level)` | 已改，**不能**用 `MatchedMultiblockRecipe.matches()` |
| 锁定校验 | `matchOneGroup` → `recipe.matches(input, level)` | 已改（存档重载后走这条） |
| **基类开工** | `AbstractMultiblockTile.startRecipe` 内部的 `matched.matches(input)` | **靠 mixin 重定向** |

最后一条是 `protected` 方法内部调用，没有可覆写点，只能 mixin：

```java
@Mixin(AbstractMultiblockTile.class)
public abstract class AbstractMultiblockTileMatchesMixin {
    @Redirect(method = {"startRecipe", "consumeRecipeInputs"},
            at = @At(value = "INVOKE", target = "...MatchedMultiblockRecipe;matches(...)Z"))
    private boolean gt$matchThroughRecipe(MatchedMultiblockRecipe self, MultiblockRecipeInput input) {
        return GTRecipeMatcherBridge.matches(self, input, GTRecipeMatcherBridge.levelOf(this));
    }
}
```

`GTRecipeMatcherBridge` 只对 `GTChemicalReactionRecipe` 走 `recipe.matches()`，**其他 mod 的配方保持 AMI 原逻辑**——不要越权改别人配方的行为。

> **排查经验**：症状是「精确匹配的配方能跑，带组件的宽松配方不开工」。因为 AMI 的快照比较对无组件的物品恰好等价于精确匹配，所以只有 `any_components` 条目会暴露问题。
>
> 定位手段：在 `GTReactionMatcher.plan()` 里打日志，看 `(loose)` / `(exact)` 标记和池内容。如果**一条 plan 日志都没有**，说明卡在链路前段（配方没找到），而不是匹配规则本身。

### 2.10 批量/并行倍数的搜索（性能）

`maxFeasibleMultiplier` 不要在 `wanted` 上逐个 `--` 试 `fits()`。两层收窄：

```java
// 第一层：除法算上界。需求随倍数线性增长，库存整除即是天花板
long coverable = GTReactionMatcher.capacity(inputs, baseCopies, itemPool, fluidPool);
// 第二层：fits 对倍数单调，二分
while (high - low > 1) {
    int middle = (low + high) >>> 1;
    if (fits(recipe, middle)) low = middle; else high = middle;
}
```

**必须给 `capacity` 的返回值封顶**。配方没有可数输入时会返回 `Long.MAX_VALUE`，直接拿去缩放会构造出撑爆堆的列表：`MAX_SEARCHED_MULTIPLIER = 1 << 16`。

> 二分的前提是「1 份一定可行」，但输出空间满了的话 1 份也开不了工——所以 `fits(recipe, 1)` 要显式验证，不能假设。

## 三、资源文件（9 类）

命名约定：方块 id `xxx_controller`，结构文件名 `xxx`。

### 3.1 结构文件（两份！）

`data/goldentweaks/multiblock/structures/vacuum_cooler.json`
`assets/goldentweaks/multiblock/structures/vacuum_cooler.json`

```json
{
  "layers": [
    ["xxx", "xxx", "xxx"],
    ["xxx", "xox", "xax"],
    ["xxx", "xxx", "xxx"]
  ],
  "keys": {
    "a": { "block": "goldentweaks:vacuum_cooler_controller" },
    "x": "#goldentweaks:multiblock/vacuum_cooler_casing"
  },
  "master": "a",
  "any": "o"
}
```

**语义**：

- `layers`：从**底层**往上，每层从北往南，每行从西往东
- `a`：主机位置（`master`）
- `x`：机壳格，指向标签
- `o`：结构空位（`any`），可放任意方块、不计数、不校验

### 3.2 机壳标签

`data/goldentweaks/tags/block/multiblock/vacuum_cooler_casing.json`

**这是限制端口种类的手段**，不需要写任何校验代码：

```json
{
  "replace": false,
  "values": [
    "#c:multiblock/input/item",
    "#c:multiblock/input/fluid",
    "#c:multiblock/input/energy",
    "#c:multiblock/output/item",
    "#c:multiblock/output/fluid",
    "goldentweaks:input_bus",
    "goldentweaks:auto_input_bus",
    "goldentweaks:output_bus",
    "goldentweaks:input_catalyst",
    "goldentweaks:shell_aluminum"
  ]
}
```

排除了 `chemical`（料斗）与 `essentia`（罐），于是这两种仓室根本不算这堵墙——扫描、投影、一键建造三处自动一致。

**必须包含仓室标签**，否则仓室放不进结构。可以照抄 `#goldentweaks:multiblock/ports`（全端口），也可以像上面这样自己列子集。

### 3.3 方块状态

`assets/goldentweaks/blockstates/vacuum_cooler_controller.json`

384 个变体 = `facing(6) × mirrored(2) × running(2) × crafting(2) × roll(4) × formed(2)`。

三种状态位含义：

| 属性 | 含义 | 贴图 |
|---|---|---|
| `formed=false` | 未成型 | `_unconstructed` |
| `formed=true, running=false` | 已成型但关机 | `_off` |
| `formed=true, running=true, crafting=false` | 已成型、开机、空闲 | 基础态（idle） |
| `formed=true, crafting=true` | 正在跑配方 | `_working` |

用脚本生成，别手写。

### 3.4 方块模型（32 个）

每个状态 × 每个 roll × 镜像/非镜像。

**四个状态各自的三层结构**：

| 状态 | 层数 | 第三层 |
|---|---|---|
| idle | 3 | `#name`（名称牌） |
| off | 2 | 无 |
| working | 3 | `#arrow`（箭头） |
| unconstructed | 2 | 无 |

**最快的做法**：复制现有机器（进阶釜）的 32 个模型，只把 `textures` 里的 shell 与各层路径替换掉，`elements` 一个字节都不动。手写会丢层级、丢 `rotation`。

**roll 旋转**：`_roll1/2/3` 要给 `overlay`、`name`、`arrow` 三个面写 `"rotation": 90/180/270`。漏了的话左键旋转主机纹丝不动。

**镜像**：
- `overlay` 的 UV 翻转为 `[16, 0, 0, 16]`
- `name` / `arrow` 换成 `_mirrored` 专用贴图（见下）

### 3.9 配方目录

`data/goldentweaks/recipe/vacuum_cooling/*.json`

目录名必须等于 `GTXxxRecipes.DIRECTORY`。**空目录机器不会报错，但什么都不会做。**

**「按 id 匹配、忽略组件」的写法**（用于修复磨损件这类配方）：

```json
{
  "inputs": [
    { "item": "mio_icif:reactor/item_reactor_coolant_six", "count": 1, "any_components": true }
  ],
  "outputs": [
    { "item": "mio_icif:reactor/item_reactor_coolant_six", "count": 1 }
  ]
}
```

`any_components: true` 表示只要物品 id 对就行，不看组件。输出写干净栈即可——带组件的输入产出不带组件的成品，就是「修复」的语义。

> **物品 id 抄错不会有任何报错**。SI 自己的 id 就不统一：`item_reactor_collant_simple` / `item_reactor_collant_triple` 是 `collant`（拼错的），`item_reactor_coolant_six` 是 `coolant`。务必从 jar 里 `assets/<mod>/models/item/` 的实际路径核对，别凭记忆写。

**显示侧也要保留组件**。端口界面列出内容时，如果只传 id 就会把用过的件显示成新的：

```java
// 错：组件丢失，用过的冷却单元显示成满耐久
new GTReactionStack(Kind.ITEM, id, count, Optional.empty());
// 对：GTReactionStack.item() 用 DataComponentPatch.CODEC 编码整个组件集
GTReactionStack.item(stack);
```

并且要保证 codec 的 `encode()` 也把组件写回去——只读不写的话，快照存了也传不到客户端，界面照样显示错的。

## 六、已经踩过的坑

| 现象 | 根因 |
|---|---|
| 放置方块直接崩溃 | 注册方块时没传实体工厂，或工厂与方块实体类型不匹配 |
| 界面一打开就关闭 | ① 客户端没注册 Screen ② `menuType()` 没覆写 ③ `stillValid()` 硬编码了基础版方块 id |
| 右键主机完全没反应 | 同上，屏幕未注册是最常见的一条 |
| 投影仪完全没反应 | ① `structureForHost` 只认基础版 ② 结构文件缺 `assets/` 那份 |
| 左键旋转无效果 | 模型缺 `"rotation"` 字段 |
| 镜像时名字位置不对 | 缺 `_name_mirrored` / `_arrow_mirrored` 贴图 |
| 拆除还回错误方块 | `createHostStack()` 硬编码了基础版物品 |
| 机器完全不工作 | 配方目录为空，或配方类型没注册 |
| **仓室放了变紫黑方块** | 端口 blockstate 没有本机机壳索引（如 `casing=2`）的变体 |
| 方块破坏后什么都不掉 | 缺战利品表 |
| 并行上限框能输入超过硬件的值 | 客户端 `commitPane` / `echoPane` 与服务端 `setParallelLimit` 三处都要夹 |
| **精确配方能跑、带组件的宽松配方不开工** | 匹配链路某处仍走 `MatchedMultiblockRecipe.matches()`（冻结快照）；基类 `startRecipe` 那处只能 mixin |
| 换了 UI 贴图但 EMI 面板盖住侧栏 | 屏幕子类没补 `addScreenBoundsProvider`（EMI 按精确类匹配） |
| 端口界面把用过的件显示成新的 | `contents()` 构造 `GTReactionStack` 时丢了组件；且 codec `encode()` 也要写回 |
| 配方里物品 id 写错但毫无报错 | 机器只是永远不开工；从 jar 的 `models/item/` 路径核对 |

## 七、以后的扩展方向

如果要加**同一台账下多种机壳**（某格可放聚乙烯或聚丙烯）：结构文件的机壳标签里并列列出即可，`GTMultiblockBuilder.casingFor()` 会取第一个非仓室成员；投影仪按每格自己的符号解析，不同符号可用不同标签，无需改代码。

如果要加**不同形状**的机器：新建结构文件即可，不需要新增 Java 类——方块只需传自己的 `structurePath`。

如果要加**限制端口种类**的机器：不必写校验，把它自己的机壳标签子集写出来即可（见 3.2）。

如果要加**新的并行/超频控件**：在 `GTMultiblockBlocks` 注册物品、加 `item/generated` 双层模型（`layer0` 底板上色、`layer1` 图标）、在 `GTMultiblockClientExtensions` 注册 tint，再按 `CONTROL_CIRCUIT_*` 的模式挂到界面。
